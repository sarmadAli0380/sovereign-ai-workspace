# 2.5 — Wiring Ollama into the harness: verified integration design

**Status:** Implemented and live-verified (2026-08-06)
**Depends on:** 2.1 (model), 2.2 (engine), ADR 1.3/1.4 (the provider shape this reuses)

## How to read this document

Phase 1's ADRs were written in a confident register and turned out to
contain five factual errors about `pi-ai` — each found during
implementation, at implementation cost. The failure wasn't bad design, it
was **unverified assertion**.

So every claim below is marked:

- **[VERIFIED]** — checked against the installed package or a live server,
  with the evidence inline.
- **[UNVERIFIED]** — believed, not yet proven. Treat as a risk, not a fact.

If a statement carries no marker, it is a *decision* (a choice we made),
not a *fact* (a claim about the world that could be wrong).

## What this reuses rather than invents

ADR 1.3 specified a `Model<'openai-completions'>` with a custom `baseUrl`
for the LiteLLM gateway. That shape was designed in Phase 1 and never
exercised. Ollama uses the identical mechanism, so this is the first real
use of it rather than new design.

**[VERIFIED]** Ollama exposes an OpenAI-compatible endpoint:

```
$ curl -s http://localhost:11434/v1/models
{"object":"list","data":null}
```

## Two silent-failure bugs found before writing any code

Both are the same class as the `maxTokens`-on-codex bug that took a live QA
pass to find in Phase 1. Both would have shipped.

### (a) `maxTokensField` must be overridden — **[VERIFIED]**

`detectCompat` (`api/openai-completions.js:1112`) branches on provider id
and `baseUrl` substrings. It has **no case for Ollama or localhost**, so an
Ollama model falls through to the OpenAI defaults, including
`maxTokensField: "max_completion_tokens"`.

Ollama ignores that field. Measured, same prompt and limit of 16:

```
max_tokens:            completion_tokens=16   finish=length   BOUNDED
max_completion_tokens: completion_tokens=156  finish=stop     IGNORED
```

Without an explicit override, `maxTokens` is a silent no-op — exactly the
codex failure repeated. **`compat: { maxTokensField: "max_tokens" }` is
mandatory, not optional.**

### (b) `contextWindow` must NOT be the advertised number — **[VERIFIED]**

The model advertises 262144, and `ollama show qwen3:4b` confirms
`context length 262144`. The server does not serve that:

```
$ curl -s http://localhost:11434/api/ps
model: qwen3:4b | context served: 4096 | vram: 3.17 GB
```

Ollama's default serving context is **4096** unless `OLLAMA_CONTEXT_LENGTH`
or a per-request `num_ctx` says otherwise — a 64× overstatement.

This one is nastier than (a) because it fails *silently and confusingly*.
`ConversationManager` sizes its budget from `Model.contextWindow`
(1.5). Given 262144 it would compute a ~245k budget, fill it, and report
itself healthy — while Ollama discarded everything past 4096. The
symptom would be a model that "forgets", with the harness's own accounting
insisting nothing was dropped.

**Decision: `Model.contextWindow` must reflect what is actually served, not
what the model claims.** Whatever `OLLAMA_CONTEXT_LENGTH` is set to is the
number that goes in the config.

## Memory arithmetic for the context choice

**[VERIFIED]** baseline: `qwen3:4b` at 4096 context occupies **3.17 GB**,
of which ~2.5 GB is weights — so ≈0.67 GB of KV cache and overhead at 4096,
≈0.16 MB/token.

**[VERIFIED — corrected 2026-08-05 by 2.4]** Linearity was assumed here and
has since been measured; it holds *exactly*, at 148,480 B/token. The
original table divided a single data point and so folded the fixed overhead
into the per-token rate, running ~15% high throughout. Corrected:

| Context | KV | Total | On 8 GB |
|---|---|---|---|
| 4096 | 0.60 GB | 3.17 GB | Comfortable **[measured]** |
| 8192 | 1.21 GB | 3.78 GB | **Recommended** **[measured]** |
| 16384 | 2.43 GB | 4.99 GB | Past the fit boundary — spills to CPU **[measured]** |
| 32768 | 4.87 GB | 7.43 GB | No |
| 262144 | 38.92 GB | 41.48 GB | Absurd |

Every conclusion below survived the correction. The one thing the original
got wrong beyond the constant: 16384 was called "tight" but is in fact past
the point where Ollama offloads layers to CPU on this machine — measured
`size_vram < size` at 14336 and above. See `2.4-gpu-sizing-math.md` for the
formula, the fit boundary, and why the ceiling moves with whatever else is
running.

**Decision: serve 8192 and set `contextWindow: 8192`.** Doubles the default
with comfortable headroom, and is enough to exercise 1.5's truncation
against a real window — which is the point of the exercise.

**Live deployment correction, 2026-08-06:** the default Ollama app process
was still serving 4096 even though the repository declared 8192. The 8192
configuration passed when started explicitly with
`OLLAMA_CONTEXT_LENGTH=8192`, using 3,777,935,441 bytes of GPU residency on
the 8 GB M3 host. `verify-live.ts` now reads `/api/ps` after the run and
fails if the served window differs from the harness budget. The deployment
must enforce this environment setting; documenting 8192 is not enough.

## Provider registration

**[VERIFIED]** `createProvider()` requires `auth` (`models.d.ts:153`:
*"Required — every provider has auth semantics, even ambient/keyless
ones"*). ADR 1.4 left open whether a local endpoint needs a key. `pi-ai`'s
own type documentation answers it (`auth/types.d.ts:210`):

> At least one of `apiKey`/`oauth` must be present: even ambient-credential
> providers and **keyless local servers provide `apiKey` auth whose
> `resolve()` reports whether the provider is configured.**

**[VERIFIED]** `resolve()` returns `AuthResult | undefined`, where
`undefined` means *not configured*, and `AuthResult` is
`{ auth: ModelAuth, env?, source? }` with `ModelAuth = { apiKey?, headers?,
baseUrl? }`.

So for Ollama: return a non-`undefined` result with a placeholder key. The
value is irrelevant — Ollama does not check it — but returning `undefined`
would mark the provider unconfigured and make it unusable.

**[UNVERIFIED]** that Ollama ignores the key entirely. Untested; a dummy
value is sent regardless, so this is low-risk either way.

## Compat flags: what does NOT need overriding

**[VERIFIED]** I predicted several flags would need overrides. That was
wrong, and the evidence says so. Ollama accepted every one without error:

```
store:true          ok        developer role      ok
system role         ok        reasoning_effort    ok
```

Ollama ignores unknown fields rather than rejecting them. So only
`maxTokensField` needs an override — and note the asymmetry that makes this
dangerous: *tolerance is not support*. Every field above returned `ok`, and
`max_completion_tokens` also returned `ok` while doing nothing. **Accepting
a parameter and honouring it are different things, and only the second was
worth testing.** That is the generalisable lesson from this pass.

**[UNVERIFIED]** `thinkingFormat`. `qwen3:4b` reports a `thinking`
capability, and the compat surface offers `"qwen"` (top-level
`enable_thinking`) and `"qwen-chat-template"` variants against a default of
`"openai"` (`reasoning_effort`). Whether the default silently disables
thinking is untested. **Not blocking** — tool calling worked without it —
but it means we may be leaving model capability unused.

## Tool calling

**[VERIFIED]** Works cleanly through the OpenAI-compatible endpoint,
closing 2.1's open item:

```
finish_reason: tool_calls
tool_calls   : 1
   -> get_weather {"city":"Paris"}
content leak : ''
usage        : {'prompt_tokens': 144, 'completion_tokens': 253, 'total_tokens': 397}
```

No content leak, so the Qwen3.5 renderer bug (2.1) does not affect
`qwen3:4b`. The model choice is vindicated empirically rather than by
reputation.

## Token accounting

**[VERIFIED]** Ollama reports `prompt_tokens` / `completion_tokens` /
`total_tokens`. That makes the Codex-style hybrid available here: anchor on
the provider's actual count and estimate only the delta since the last
response, rather than re-estimating the whole conversation with a heuristic
measured to underestimate code by 1.37×.

Deferred to a separate change — it modifies 1.5 and should not ride along
with this integration.
