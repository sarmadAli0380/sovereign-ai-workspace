# 2.2 — Inference engines: Ollama, vLLM, llama.cpp

**Status:** Decided for this hardware (2026-08-04)
**Depends on:** 2.1 (model choice)

## The decision is partly made for us

The roadmap presents three engines as a choice. On an **Apple M3 with 8 GB**,
one of them isn't a choice at all:

**vLLM is unavailable on this machine.** It targets NVIDIA CUDA (with some
ROCm/TPU support); there is no practical Apple Silicon path. This is not a
preference, it's a hard exclusion. It still has to be *understood* — a client
running production inference on real GPUs is exactly who vLLM is for, and
sizing their hardware is Phase 2's client-facing deliverable — but it cannot
be run or benchmarked here.

That leaves Ollama and llama.cpp, which are less of a comparison than they
look: **Ollama is a wrapper around llama.cpp** (plus a model registry, a
server, and lifecycle management). Choosing between them is choosing how much
of the plumbing to own, not choosing an inference implementation.

## Decision: Ollama

Three reasons, in order of weight for this project:

**1. It exposes an OpenAI-compatible endpoint at `/v1`.** This is the one
that actually matters. `http://localhost:11434/v1` maps directly onto the
`Model<'openai-completions'>` + custom `baseUrl` shape that ADR 1.3 already
specified for the LiteLLM gateway — a shape designed, documented, and never
exercised in Phase 1. Wiring a local model in becomes the *first real use of
a mechanism Phase 1 already built*, rather than new integration work.

Verified before pulling any model:

```
$ curl -s http://localhost:11434/v1/models
{"object":"list","data":null}
```

OpenAI's response shape, `data: null` only because nothing was installed yet.

**2. Model lifecycle is handled.** Pull, cache, load/unload on demand, and
serve concurrently. With llama.cpp directly, that is all manual: source a
GGUF, manage the file, run `llama-server` with the right flags per model.
Real work, and none of it is what Phase 2 is trying to learn.

**3. It's the fastest path to a running system**, which the roadmap names as
Ollama's explicit reason for existing.

The cost is control. Ollama picks quantization and runtime flags for you
unless overridden, which is exactly what 2.3 has to look at rather than
accept blindly.

## When each is actually the right answer

The portable version of this, for advising a client:

| Engine | Right when | Wrong when |
|---|---|---|
| **Ollama** | Dev machines, prototypes, single-user or low-concurrency deployments, fastest time-to-running | High-throughput serving — no continuous batching, so concurrent users queue |
| **vLLM** | Production serving on NVIDIA GPUs, many concurrent users. PagedAttention + continuous batching give order-of-magnitude better throughput under load | No NVIDIA GPU; single-user workloads where the complexity buys nothing |
| **llama.cpp** | CPU-only or edge/constrained hardware, or when you need control over quantization and runtime flags that Ollama abstracts away | You'd be rebuilding Ollama's lifecycle management by hand for no gain |

The distinction worth carrying into client conversations is **throughput vs.
time-to-running**. Ollama serves requests one at a time; vLLM's continuous
batching is what makes concurrent users viable. A client asking "can this
serve our whole team?" is asking a vLLM question, and the answer depends on
concurrency, not model size.

## Apple Silicon specifics

Ollama ships **MLX-optimized** builds for Apple Silicon on the smaller sizes.
MLX is Apple's own array framework, built for unified memory, and should beat
the generic GGUF/Metal path on an M-series chip. Worth measuring rather than
assuming — flagged for 2.5, not claimed here.

Unified memory also changes the usual mental model: there is no separate
VRAM pool to size against. Model weights, KV cache, the OS, and every other
process draw on the same 8 GB. That makes the sizing math in 2.4 *stricter*
here than on a discrete-GPU box, not looser.
