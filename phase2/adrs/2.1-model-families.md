# 2.1 — Open-weight model families, and picking one per use case

**Status:** Decided for this hardware (2026-08-04)
**Depends on:** Phase 1 harness (the model is swappable, so this decision is reversible by config)

## The constraint that drives everything here

This machine is an **Apple M3, 8 GB unified memory**, 57 GB free disk.

That is the single most important input to this decision, and it invalidates
the roadmap's stated target before any model comparison starts. The roadmap
says "stand up a quantized 7–13B model." On 8 GB of *unified* memory — shared
between macOS, the GPU, and everything else — that is not achievable:

| Model | Ollama download | Verdict on 8 GB |
|---|---|---|
| `qwen3.5:9b` | 6.6 GB | No — leaves nothing for the OS |
| `qwen3:8b` | 5.2 GB | No — swaps under any real context |
| `qwen3:4b` | **2.5 GB** | **Workable, with headroom for KV cache** |
| `qwen3.5:4b` | 3.4 GB | Workable |
| `qwen3.5:2b` | 2.7 GB | Comfortable |

macOS alone holds ~3–4 GB. A model file is not the whole cost either — the
KV cache grows with context length and is charged on top (see 2.4).

**So the honest target on this hardware is 4B, not 7–13B.** Recorded as a
constraint rather than quietly substituted, because the roadmap's number is
what someone would check against later.

This does not weaken Phase 2's actual goal. The point is to prove the harness
routes to a self-hosted backend and that the swap is a config edit — that is
model-size-independent. Sizing *clients'* hardware for larger models is 2.4's
job, and can be done as math without owning the GPU.

## What's actually current, checked rather than recalled

Model families move fast enough that this needed verifying against Ollama's
live library, not memory. Two corrections to what I'd have said otherwise:

- **Qwen2.5 is two generations behind.** Current is **Qwen3.5** (0.8B–122B),
  with **Qwen3.6** for agentic coding (27B/35B only — both far past this
  machine's ceiling).
- The generational jump matters less than the tool-calling plumbing, below.

## The decision: `qwen3:4b`, not the newest thing

Chosen deliberately over the newer Qwen3.5, on one criterion that outranks
raw capability for this project: **tool calling has to actually work.**

Qwen3.5's tool calling is currently broken in Ollama. Its registry maps
Qwen3.5 to the Qwen3 Hermes-style JSON renderer, but Qwen3.5 was trained on
the Qwen3-Coder XML format. The correct renderer exists in Ollama's codebase
and is only wired to `qwen3-coder`. Open issue: *"qwen3.5:9b sometimes prints
out tool call instead of executing it."*

Meanwhile `qwen3` is the model Ollama's own tool-calling documentation uses
in every example, and it is the family the Hermes renderer is correctly
mapped to.

The reasoning is specific to what this phase is for: the harness's
`ToolRegistry`/`dispatchToolCall` is being validated against a second
provider. A model whose tool calls are unreliable for renderer reasons would
produce failures that *look* like harness bugs. Phase 1 already spent real
effort separating "harness defect" from "flaky environment"; picking a model
with a known tool-calling defect would manufacture that ambiguity on purpose.

Newer is the wrong axis here. Working is the right one.

### Selection criteria, ranked for this use case

1. **Tool-calling reliability** — this is what Phase 2 exists to exercise
   through the harness. Decisive.
2. **Memory footprint** — a hard gate at 8 GB, not a preference.
3. **Context length** — `qwen3:4b` carries 256K, notably larger than the 40K
   on `qwen3:8b`/`14b`. Useful for testing 1.5's truncation against a real
   window, though KV cache means the usable figure is far lower here (2.4).
4. **License** — Qwen3 is Apache-2.0, which matters for the client-delivery
   goal: a client can be handed the stack without a bespoke license
   conversation. Llama's community license carries an acceptable-use policy
   and an MAU threshold; fine for most clients, but one more thing to check.
5. **Multilingual** — Qwen is consistently strong here, and it is directly
   relevant to the Gulf/Riyadh client base the roadmap names.

## The families, and when each is the right answer

Kept brief and non-committal on rankings, which go stale fast. What holds:

- **Qwen (Alibabaced)** — the strongest small-model family for multilingual
  and reasoning, and the pragmatic default under ~32B. Apache-2.0.
- **Llama (Meta)** — the safe English-first default with the deepest
  ecosystem and tooling support. Community license, not OSI-open.
- **Mistral** — strong on agentic/JSON output, with native function calling;
  the interesting sizes (Small 24B) are out of reach on 8 GB.
- **DeepSeek** — reasoning-focused, with the useful sizes well past this
  hardware.

The genuinely portable lesson is that **there is no "best" open model, only a
best fit per constraint** — and the binding constraint is usually memory and
license, not benchmark scores. That is the shape of the question a client
actually asks.

## What makes this decision cheap to reverse

Because of Phase 1: swapping model or family is a `model.config.json` edit.
That is exactly the property Phase 1 was built to provide, and it is why
committing to a 4B model now costs little — if `qwen3:4b`'s tool calling
disappoints in practice, changing it is one line, and demonstrating that is
itself a Phase 2 result.
