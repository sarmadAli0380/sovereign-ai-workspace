# 2.4 — GPU sizing math: what a served model actually costs in memory

**Status:** Measured (2026-08-05)
**Depends on:** 2.1 (model), 2.2 (engine), 2.3 (bytes per weight)
**Closes:** the `[UNVERIFIED]` KV-cache table in `2.5-local-provider-integration.md`

## How to read this document

Same convention as 2.5: **[VERIFIED]** means checked against a live server
with the evidence inline, **[UNVERIFIED]** means believed but not proven,
and an unmarked statement is a *decision* rather than a claim about the
world.

The difference from 2.5 is that this document is almost entirely the first
kind. Sizing is arithmetic, and arithmetic can be run.

## The problem this solves

The roadmap's phrasing is "size hardware for a client without guessing."
The guessing happens in a specific place: everyone can multiply parameters
by bytes-per-weight to get the model size, and then the KV cache — the term
that actually varies with how the system is *used* — gets hand-waved as
"plus some overhead." That term is the one that decides whether a box
works, because it scales with context and with concurrency, and it is the
one a client's requirements move.

2.5 shipped with a KV table marked `[UNVERIFIED]` that assumed linear
scaling from a single data point. This measures it.

## The formula

```
total = weights + fixedOverhead + (contextTokens × sequences) × (kvPerToken + runtimePerToken)

kvPerToken = layers × kvHeads × (keyDim + valueDim) × kvCacheBytes
```

Implemented in `src/sizing.ts`, with every measurement below pinned as a
regression fixture in `src/sizing.test.ts`.

### Term 1 — weights

`paramCount × bitsPerWeight / 8`, or better, the on-disk file size when the
file exists. This is the term everyone already gets right.

**[VERIFIED]** 2.3 recorded `Q4_K_M` as the quantization but not its actual
rate. Measured from two real GGUF files:

| Model | Params | On disk | Bits/weight |
|---|---|---|---|
| `qwen3:4b` | 4,022,468,096 | 2,497,293,931 B | **4.97** |
| `llama3.2:3b` | 3,212,749,888 | 2,019,393,189 B | **5.03** |

**This is above the ~4.8 usually quoted for `Q4_K_M`**, and the reason is
worth carrying: K-quants keep the embedding and output tensors at higher
precision than the body of the model, so the effective rate rises as the
vocabulary grows relative to the parameter count. Both models here have
large vocabularies (152k and 128k) for their size, which is exactly the
regime where the quoted number runs low. On a 70B the quoted figure would
be closer to right.

**Decision: use 5.0 bits/weight for `Q4_K_M` on small models**, and prefer a
real file size whenever one exists — a measurement beats a rate.

### Term 2 — KV cache

```
kvPerToken = layers × kvHeads × (keyDim + valueDim) × bytesPerElement
```

**[VERIFIED]** not by inference but against llama.cpp's own allocation
report. Serving `qwen3:4b` at 4096 context with 2 parallel sequences:

```
llama_kv_cache: size = 1152.00 MiB (4096 cells, 36 layers, 2/2 seqs),
                K (f16): 576.00 MiB, V (f16): 576.00 MiB
```

1152 MiB ÷ 2 seqs ÷ 4096 tokens = **147,456 B/token**, which is exactly
`36 × 8 × (128+128) × 2`.

**The load-bearing detail is `kvHeads`, not `heads`.** `qwen3:4b` has 32
query heads and 8 KV heads; grouped-query attention caches only the latter.
Using `head_count` instead of `head_count_kv` overstates the cache by 4× on
this model, and modern models are almost all GQA. This is the single most
common way the calculation goes wrong, so `sizing.test.ts` asserts the 4×
gap explicitly rather than leaving it as a comment.

### Term 3 — runtime overhead

**[VERIFIED]** There is a per-token cost beyond the KV cache of **exactly
1024 bytes**, and it is architecture-independent:

| Model | Measured slope | KV formula | Difference |
|---|---|---|---|
| `qwen3:4b` (36 layers) | 148,480 B/token | 147,456 | **1024** |
| `llama3.2:3b` (28 layers) | 115,712 B/token | 114,688 | **1024** |

This was a prediction before the second measurement: having seen 1024 on
qwen, the open question was whether it was fixed per token or per
layer-per-token. Fixed was predicted and fixed is what llama3.2 returned —
the 28-layer model showed the same 1024, not 796.

It is 0.7% of the per-token cost. It matters for reconciling a measurement
against the formula, not for sizing a purchase.

There is also a context-*independent* overhead — tokenizer caches, output
buffer, compute graph — measured as the intercept minus the on-disk weight
size: **64.3 MB** (qwen3:4b) and **55.1 MB** (llama3.2:3b). Taken as a flat
64 MB constant rather than modelled; the error is smaller than the rounding
on any real memory budget.

## The measurements

Method: load via `/api/generate` with `options.num_ctx` set, read
`/api/ps`. Ollama 0.32.5, Apple M3, 8 GB. Unloaded between every point so
each is a fresh allocation.

### `qwen3:4b`

| Context | Measured | Predicted | Error |
|---|---|---|---|
| 1024 | 2.714 GB | 2.713 GB | −0.01% |
| 2048 | 2.866 GB | 2.865 GB | −0.01% |
| 4096 | 3.170 GB | 3.169 GB | −0.01% |
| 8192 | 3.778 GB | 3.778 GB | −0.01% |
| 10240 | 4.082 GB | 4.082 GB | −0.01% |
| 12288 | 4.386 GB | 4.386 GB | −0.01% |

Every consecutive interval has an identical slope of 148,480 B/token — not
approximately, identically. **Linearity is not an approximation here, it is
exact**, which retires the `[UNVERIFIED]` marker on 2.5's table.

### `llama3.2:3b` — does the formula generalise, or was it fitted?

A formula validated on one model is a curve fit. A second family with
different geometry (28 layers vs 36, `llama` vs `qwen3` architecture) tests
whether it generalises.

| Context | Measured | Predicted | Error |
|---|---|---|---|
| 1024 | 2.193 GB | 2.202 GB | +0.41% |
| 2048 | 2.311 GB | 2.320 GB | +0.39% |
| 4096 | 2.548 GB | 2.557 GB | +0.35% |
| 8192 | 3.022 GB | 3.031 GB | +0.30% |

Worst case 0.41%, and the error is a constant bias, not drift — it is the
flat 64 MB overhead constant, which was taken from qwen and is 9 MB
generous for llama. The *slope* is exact for both.

### Concurrency

**[VERIFIED]** KV cache is allocated per sequence, so concurrency
multiplies it. Tested by running a second Ollama on port 11435 with
`OLLAMA_NUM_PARALLEL=2` (leaving the primary server untouched):

| Configuration | Measured |
|---|---|
| 1 sequence × 8192 ctx | 3,777,935,441 B |
| 2 sequences × 4096 ctx | 3,781,678,858 B |

0.1% apart, and llama.cpp confirms the split directly: `n_ctx = 8192,
n_ctx_seq = 4096`, `2/2 seqs`. **Total cells is what costs memory; how they
are divided between sequences and context length is free.**

This is the term most likely to be missed when sizing for a client, because
it is invisible in single-user testing. A box that comfortably serves one
8k session serves *eight* 8k sessions at 8× the cache.

## Where linearity stops

At 14336 tokens the qwen3:4b line breaks:

| Context | `size` | `size_vram` | |
|---|---|---|---|
| 12288 | 4,386,109,521 | 4,386,109,521 | fully resident |
| 14336 | 4,859,208,404 | 4,567,586,569 | **spilled to CPU** |
| 16384 | 5,286,031,264 | 4,608,386,661 | **spilled to CPU** |

Past the boundary, `size_vram < size` — layers are offloaded to CPU — and
total allocation jumps *above* the linear prediction, because the split
allocates on both sides. The model still answers. It answers slowly.

**So the useful output of a sizing calculation is not a number, it is a
number plus whether it fits.** `sizing.ts` exposes `fitsIn()` alongside
`estimateMemory()` for that reason, and the tests pin the boundary: fits at
12288, does not at 14336.

## The ceiling is not a property of the machine

**[VERIFIED]** llama.cpp logs its own fitting rule on load:

```
projected to use 3606 MiB of device memory vs 5460 MiB of free device memory
will leave 1854 >= 1024 MiB of free device memory, no changes needed
```

Two things follow, and both invalidate the obvious way to size a box:

1. **The budget is free memory, not installed memory.** This machine has
   8 GB installed and reported 5460 MiB free at that moment. On unified
   memory (2.3) every other process draws from the same pool, so the number
   moves between runs — the 12288/14336 boundary above is where it happened
   to fall with that desktop open, not a constant.
2. **The runtime reserves 1 GiB and will not spend it.** Sizing against
   free memory without subtracting that reserve overstates capacity by a
   gigabyte.

`fitsIn()` takes *free* bytes and subtracts the 1 GiB reserve, and the CLI
labels its `--budget` flag as free memory for the same reason.

## A caveat on the instrument

**[VERIFIED]** `/api/ps` `size` is Ollama's own *projection*, not a
measurement of resident memory — it is the same 3606 MiB the fitting log
prints before allocating anything. Checked against the OS at one point:
`llama-server` RSS was 3,614,976 KiB = 3530 MiB against a 3606 MiB
projection, so the projection runs **2.1% high**.

That is fine, and arguably preferable — Ollama's admission decisions are
made on the projection, so predicting the projection predicts whether it
will load. But every number in this document is "what the server plans to
allocate," and it should not be quoted as measured RSS.

The KV term is exempt from this caveat: it is confirmed by llama.cpp's own
post-allocation report, not by the projection.

## Levers, in order of effect

For a client who does not fit, in the order worth trying:

1. **Smaller quantization** — linear in the weights term, the largest term.
   `Q4_K_M` → `Q4_K_S` is ~8% off the weights. Below Q4 breaks tool calling
   before it breaks chat (2.3), so this bottoms out fast for agentic work.
2. **Shorter context** — linear, and usually the cheapest concession, since
   most workloads do not use the window they ask for. 1.5's truncation
   exists precisely so a short window degrades gracefully rather than
   erroring.
3. **Fewer concurrent sequences** — linear, and the one clients
   underestimate. Throughput, not capability.
4. **Quantized KV cache** — `OLLAMA_KV_CACHE_TYPE=q8_0` halves the cache
   term. **[UNVERIFIED]** here: it needs a server restart to change, and the
   primary server is the user's. `sizing.ts` takes `kvCacheBits` so the
   arithmetic is available; the *quality* cost is unmeasured.
5. **A smaller model** — last, because it is the only one that changes what
   the system can do.

## Worked examples

```bash
node scripts/size-model.ts --model qwen3:4b --budget 5.7
node scripts/size-model.ts --params 70e9 --layers 80 --kv-heads 8 \
  --head-dim 128 --quant Q4_K_M --budget 48 --sequences 8
```

The second is the shape of a real client question — "we have an A6000, can
we serve a 70B to eight people?" — and the answer is no, by a wide margin:
43.75 GB of weights leaves under 4 GB of budget, which buys about 1024
tokens of context per sequence. That conversation is much better had with
arithmetic than after the purchase order.

Geometry comes from GGUF metadata (`/api/show` → `model_info`) or a
HuggingFace `config.json` (`num_hidden_layers`, `num_key_value_heads`,
`head_dim`). The CLI reads GGUF keys by suffix rather than by architecture
prefix, so it does not need a per-family branch — same rule the harness
follows about provider names never appearing in control flow.

## What this changes elsewhere

- `2.5-local-provider-integration.md`'s KV table was `[UNVERIFIED]` and
  approximately right: it estimated 0.7 GB of KV at 4096 against a measured
  0.60 GB, and 2.7 GB at 16384 against 2.42 GB — consistently ~15% high,
  because it folded the fixed overhead into the per-token rate by dividing a
  single data point. Its **conclusions all survive**; the table is corrected
  in place with a pointer here.
- 2.5's decision to serve 8192 is confirmed as comfortable: 3.78 GB
  measured, against a boundary near 13k.

## Failed predictions, recorded

- **Right:** the 1024 B/token overhead would be fixed per token rather than
  per layer. llama3.2:3b confirmed it.
- **Wrong:** I expected the measured slope to sit a few percent above the
  architectural formula with some noise, and to have to fit a coefficient.
  It is exact and integral — 148,480 every single interval — which is a
  stronger result than expected and meant the "formula" needed no fitting at
  all.
- **Wrong:** I expected `Q4_K_M` to measure near the widely quoted 4.8
  bits/weight. Both models came in at ~5.0, for a reason (vocabulary share)
  that only shows up on small models.

- [x] Concurrency term measured, not assumed.

- [x] Fit boundary and CPU-spill behaviour characterised.

      runtime term and the 1 GiB reserve are llama.cpp behaviours and should
