# 2.3 — Quantization: GGUF, AWQ, GPTQ, and what actually applies here

**Status:** Decided for this hardware (2026-08-04)
**Depends on:** 2.2 (engine choice determines which formats are even loadable)

## Why this matters at all

Quantization is what makes Phase 2 possible on this machine. A 4B model at
full FP16 precision is ~8 GB of weights — already the entire memory budget,
before the OS or any context. At 4-bit it's ~2.5 GB, which fits with room to
work.

The trade is precision for memory. The useful question is not "is quantized
worse" (it is, slightly) but **where the quality cliff is** — and it is
sharper below 4-bit than most size tables suggest.

## The three formats, and which are reachable

| Format | Built for | Reachable here? |
|---|---|---|
| **GGUF** | llama.cpp / Ollama. CPU and Apple Metal, with partial GPU offload | **Yes — the only one that matters on this machine** |
| **AWQ** | Activation-aware weight quantization, for GPU serving (vLLM) | No — needs CUDA |
| **GPTQ** | Post-training quantization, also GPU-serving oriented | No — needs CUDA |

AWQ and GPTQ are both **vLLM-side formats**. Since 2.2 excluded vLLM on this
hardware, they are excluded with it. They still matter for advising a client
running NVIDIA hardware, which is why they're documented rather than dropped:
if a client's production box is a real GPU, AWQ/GPTQ + vLLM is the pairing,
not GGUF.

**The pairing is the portable lesson:** GGUF↔llama.cpp/Ollama (CPU, Apple
Silicon, edge), AWQ/GPTQ↔vLLM (NVIDIA production serving). Picking a
quantization format is downstream of picking an engine, which is downstream
of the hardware. Getting that order backwards is how people end up with a
model file their runtime can't load.

## K-quants: the part the size tables hide

GGUF's `Q4_K_M`-style names decompose as:

- `Q4` — 4-bit base precision.
- `_K` — "K-quant": a smarter scheme that varies precision *per tensor* rather
  than flatly across the model, spending bits where they affect output most.
- `_M` — the size/quality tier within that scheme: `_S` (small), `_M`
  (medium), `_L` (large).

The rule of thumb worth remembering:

- **`Q4_K_M` is the default recommendation** — the standard quality/size
  sweet spot, and what Ollama serves for most `:4b`-style tags unless you ask
  otherwise.
- **`Q5_K_M`** — noticeably closer to full precision, ~25% larger. Worth it
  when memory allows.
- **`Q8_0`** — near-lossless, ~2× the size of Q4. Rarely worth it locally.
- **Below Q4 (`Q3`, `Q2`)** — this is where quality degrades fast, and where
  instruction-following and structured output (i.e. **tool calling**) break
  down before general chat does. Avoid for anything agentic.

That last point is the one that matters for this project specifically. Phase
2 exists to exercise the harness's tool dispatch against a local model; a
sub-4-bit quant is exactly the setting where a model starts emitting
malformed JSON and the failure looks like a harness bug. Same reasoning as
2.1's model choice — don't manufacture ambiguity.

## Decision: accept Ollama's default (`Q4_K_M`), verify what it actually is

Ollama picks a quantization per tag rather than exposing it in the name. The
decision here is to **take the default but confirm it**, not assume it:
`ollama show qwen3:4b` reports the real quantization, and 2.5 records it.

This is deliberate given 2.2's noted cost — Ollama abstracts these choices
away, and the point of this ADR is to know what was chosen on our behalf
rather than to inherit it silently.

## Unified memory changes the arithmetic

On a discrete-GPU machine, quantization is about fitting VRAM, and the CPU's
RAM is a separate pool. On Apple Silicon there is one pool. Model weights,
KV cache, macOS, and everything else compete for the same 8 GB — so a quant
that "fits in 8 GB" on paper does not fit in practice.

That's 2.4's arithmetic, and it's why the practical ceiling in 2.1 came out
well below the raw file size.
