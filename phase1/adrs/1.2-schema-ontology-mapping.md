# 1.2 — Unified schema: mapping onto `pi-ai`'s ontology

**Status:** Decided (research/design stage — no code yet)
**Depends on:** ADR-002 (`pi-ai` as harness interface)

## Reframing

The original 1.2 spec (see `phase1-model-agnostic-harness-expanded.md`)
called for inventing `UnifiedMessage` / `UnifiedResponse` types from zero
providers. ADR-002 changed the input to that task: `pi-ai` already ships a
typed ontology that's the harness's actual wire contract once app code only
ever talks to `pi-ai`. The job here isn't "design a schema," it's "decide
what to adopt as-is, what to add on top, and what to explicitly not
rebuild."

Verified directly against `pi-ai`'s README/source
(`earendil-works/pi`, `packages/ai`) rather than working from the spike's
summary — the shapes below are the real exported types, not a
paraphrase.

## What `pi-ai` already provides (adopt as-is)

- **`Context`** — `{ systemPrompt?, messages: Message[], tools?: Tool[] }`.
  This *is* 1.2's top-level request shape.
- **`Message`** — a union: `UserMessage | AssistantMessage |
  ToolResultMessage`, discriminated on `role`.
- **`AssistantMessage`** — `{ role: 'assistant', content: ContentBlock[],
  usage: Usage, stopReason: StopReason, responseId?, errorMessage? }`. This
  is 1.2's `UnifiedResponse`. `usage` already carries `input`/`output`
  tokens and a `cost` breakdown; `stopReason` is the harness's
  `finish_reason` (`stop | length | toolUse | error | aborted`).
- **`ContentBlock`** — `TextContent`, `ImageContent`, `ThinkingContent`,
  and `ToolCall` (`{ type: 'toolCall', id, name, arguments }`). Assistant
  messages carry an array of these instead of a single content field —
  text, thinking, and tool calls interleave in one ordered list.
- **`ToolResultMessage`** — `{ role: 'toolResult', toolCallId, toolName,
  content: (TextContent | ImageContent)[], isError, timestamp }`. Answers a
  `ToolCall` by id, matching 1.6's dispatch model directly.
- **`Tool`** — `{ name, description, parameters: TSchema }` using TypeBox,
  serializable as plain JSON. This is 1.6's `ToolDefinition`, already
  built.
- **Tool argument validation** — `validateToolCall(tools, toolCall)` is a
  built-in function that validates arguments against the TypeBox schema and
  throws on mismatch. This covers most of the "write a validator function"
  step from the original 1.2 spec, at least for tool calls.
- **Error unification** — errors and aborts already surface as a normal
  `AssistantMessage` with `stopReason: 'error' | 'aborted'` and an
  `errorMessage` field, alongside whatever partial `content` was received.
  No separate error type needed at the message level.

## What the harness adds on top

`pi-ai`'s types describe a single model call. They don't know about the
harness's own concerns: which config key resolved to which provider, or
whether a call went direct vs. through the LiteLLM gateway (ADR-002),
or how long the call took end to end. None of that belongs inside
`pi-ai`'s types — it wraps them.

Working name: **`HarnessResult`** —

```
HarnessResult {
  message: AssistantMessage   // untouched pi-ai type
  configKey: string           // which model.config.json entry resolved this call
  routedVia: 'native' | 'gateway'   // ADR-002's routing choice, made visible
  latencyMs: number
}
```

This is additive-only: nothing about `pi-ai`'s own shape is repacked or
renamed. The original spec's `raw_provider_metadata` passthrough field
turns out to be mostly unnecessary at the schema level — `responseId` is
already on `AssistantMessage`, and raw request/response inspection has a
dedicated mechanism (`onPayload` / `onResponse` callbacks) rather than
needing to live in the persisted schema.

**Harness-level error wrapping** (noted in `findings-log.md` as something
that stays owned regardless of `pi-ai`): specifically for failures that
happen *before* `pi-ai` is reached — bad `configKey`, missing API key,
gateway unreachable. These should resolve to the same `HarnessResult`
shape (an `AssistantMessage`-like object with `stopReason: 'error'`) so a
caller checks one place for failure, regardless of whether the failure was
inside or outside `pi-ai`'s reach.

## What's explicitly not being rebuilt

- No custom `UnifiedMessage` type — `pi-ai`'s `Message` union is used
  directly.
- No custom tool-schema validator — `validateToolCall` covers it.
- No custom usage/cost tracking shape — `Usage` already has it.

## Pre-flight validation — the one gap

`pi-ai` validates tool call *arguments* once a call comes back, but nothing
validates a `Context` going *in* — e.g., an empty `messages` array, a tool
whose `parameters` isn't a valid TypeBox schema, or a `configKey` that
doesn't resolve to any registered provider. This is a real, narrow gap:
a thin `validateContext(context, configKey)` guard at the harness boundary,
run before handoff to `pi-ai`, catching harness-specific misconfiguration
early rather than letting it surface as a confusing provider-level error.

## Definition of done (revised)

The original DoD ("schema file committed, unit tests covering 3 example
payloads") doesn't fit anymore — there's no schema file to write, `pi-ai`'s
types are already tested upstream. Revised:

- [ ] `HarnessResult` type documented (this file) — done.
- [ ] `validateContext()` guard's exact checks listed (empty messages,
      malformed tool schema, unknown configKey) — not yet itemized in
      detail, next pass.
- [ ] Confirm the config-routing shape from 1.4 (`model.config.json`) has a
      slot for `configKey` and `routedVia` so `HarnessResult` can actually
      be populated once 1.4 exists.

Still research-stage — no code written yet, per current focus.
