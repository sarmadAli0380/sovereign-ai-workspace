# 1.3 — Provider adapters: scope under the `pi-ai` decision

**Status:** Decided (research/design stage — no code yet)
**Depends on:** ADR-002 (`pi-ai` as harness interface), 1.2's schema mapping

## Reframing

The original 1.3 spec (`phase1-model-agnostic-harness-expanded.md`) called
for hand-building two adapters — `adapter.chat()` request translation,
response translation back to `UnifiedResponse`, repeated per provider —
using OpenAI + Anthropic specifically because their formats differ enough
to prove the abstraction.

Under ADR-002, that translation code doesn't need to be written. `pi-ai`'s
built-in provider factories (`getModel('anthropic', ...)`,
`getModel('openai', ...)`) already are adapters in the GoF sense from
`roadmap-concept-map.md` — one target interface (`Context` in,
`AssistantMessage` out), multiple incompatible concrete implementations
behind it. Calling `getModel('openai', 'gpt-4o-mini')` vs.
`getModel('anthropic', 'claude-sonnet-4-...')` and passing either into the
same `complete()`/`stream()` call *is* the adapter pattern, already built
and tested upstream by `pi-ai` itself.

So 1.3 isn't "build two adapters" anymore. It's "confirm the two native
adapters already meet the bar, and scope the one adapter that's actually
new" — the LiteLLM-gateway provider from ADR-002.

## What's already proven vs. what isn't

From the 1.1 spike and ADR-002:

- **Anthropic, direct** — proven live. Spike ran a real tool-calling test
  through `pi-ai`'s Anthropic provider and got a correctly-typed response
  (a `401` in the sandbox, but structurally valid — confirms the wire
  format round-trips).
- **Anthropic, via LiteLLM gateway** — proven live. ADR-002 stood up a
  LiteLLM proxy locally, registered it as a custom `pi-ai` provider, and
  got a standard `AssistantMessage` back, routed through to real Anthropic.
- **OpenAI, direct** — **not yet proven.** The spike's own notes flag this:
  "OpenAI's endpoint wasn't reachable from this sandbox's network rules...
  worth a quick retry with real keys in your own environment."
- **OpenAI, via LiteLLM gateway** — **not tested at all.** Only the
  Anthropic leg went through the gateway in ADR-002's verification.

This matters because 1.3's original definition of done was schema
conformity *across two genuinely different provider formats* — that claim
is only half-verified right now. `pi-ai` almost certainly handles OpenAI's
format correctly (it's one of the library's primary supported providers,
not an edge case), but "almost certainly" isn't the same as "verified in
this project," and the whole point of 1.1's spike was not taking that on
faith.

## The one adapter that is new: the LiteLLM-gateway `Model`

Native providers need zero adapter code. The gateway path needs one
`Model<'openai-completions'>` object — `pi-ai`'s own docs give this almost
verbatim as a documented pattern for exactly this use case (not something
invented for this project):

```typescript
const litellmModel: Model<'openai-completions'> = {
  id: 'gpt-4o',                    // or whichever model the proxy exposes
  name: 'GPT-4o (via LiteLLM)',
  api: 'openai-completions',
  provider: 'litellm',
  baseUrl: 'http://localhost:4000/v1',
  reasoning: false,
  input: ['text', 'image'],
  cost: { input: 2.5, output: 10, cacheRead: 0, cacheWrite: 0 },
  contextWindow: 128000,
  maxTokens: 16384,
  compat: {
    supportsStore: false,   // LiteLLM doesn't support the `store` field
  }
};
```

`pi-ai` calls out LiteLLM by name as one of the cases needing
`compat.supportsStore: false` — this isn't a workaround we're inventing,
it's the documented integration point.

**Open question this raises:** `cost` here is hardcoded per model. If
LiteLLM is doing its own spend tracking (its whole reason for existing per
ADR-002), does the harness need accurate `cost` figures on the `pi-ai` side
too, or is that redundant/conflicting with LiteLLM's own metering? Worth
resolving before Phase 5, not urgent now.

## Scope decision for Phase 1

ADR-002 already says gateway routing "becomes relevant starting around
Phase 5, not Phase 1." Consistent with that: **Phase 1's adapter
requirement is satisfied by native Anthropic + OpenAI coverage alone.**
The gateway `Model` definition above is documented and ready, but doesn't
need to be exercised again until a multi-tenant (Phase 5) need actually
shows up — re-verifying it now would be proving something ADR-002 already
proved once.

What Phase 1 *does* still owe, to close the real gap:

1. Retry the OpenAI leg with real keys (the spike's own flagged follow-up)
   — confirms native OpenAI coverage the same way Anthropic was confirmed.
2. Nothing else to build. No adapter modules, no shared test suite to
   author from scratch — if a shared conformity check is wanted, it's
   "run the same prompt through `getModel('anthropic', ...)` and
   `getModel('openai', ...)`, diff the two `AssistantMessage` shapes,"
   which is a verification script, not adapter code.

## Definition of done (revised)

- [ ] OpenAI leg verified live (Anthropic already was, in the spike).
- [ ] Native Anthropic + OpenAI `AssistantMessage` outputs diffed for
      schema conformity on the same prompt (not yet run).
- [x] LiteLLM-gateway `Model` definition documented (this file) — deferred
      re-verification to Phase 5 per ADR-002's own scoping.

Still research-stage — no code written yet.

## Correction (found while researching 1.4)

The `getModel('anthropic', ...)` / `getModel('openai', ...)` calls above
are illustrative of the *pattern* (one lookup call swaps the provider),
but not the actual current API. Root `@earendil-works/pi-ai` doesn't
export a flat `getModel()` — that only exists via the deprecated
`/compat` subpath. The real current pattern is `pi-ai`'s `Models`
registry (`createModels()` / `builtinModels()` / `Models.getModel()`),
worked out in full in `1.4-config-routing-design.md`. Doesn't change
anything decided here — native providers still need no adapter code — but
if you're writing the actual verification script for the OpenAI leg, use
`builtinModels().getModel('openai', ...)`, not the flat call shown above.
