# 1.6 — Provider-agnostic tool-calling design

**Status:** Decided with the user (research/design stage — no code yet)
**Depends on:** `1.2-schema-ontology-mapping.md` (Tool/ToolCall/ToolResultMessage types), `1.5-conversation-manager-design.md` (where results get appended)

## What's already solved (same pattern as 1.2/1.3)

The original 1.6 spec called for a `ToolDefinition` schema, a
`translateTools(tools, provider)` per adapter, and a `dispatchToolCall`.
Two of those three are already handled by `pi-ai`, same shape of finding
as 1.3's provider adapters:

- **`ToolDefinition`** — `pi-ai`'s `Tool` type (`name`, `description`,
  `parameters` as a TypeBox schema) already is this. Nothing to design.
- **`translateTools(tools, provider)`** — `pi-ai` translates tool schemas
  into each provider's native tool-call format internally, inside each
  provider's `stream()`/`complete()`. Not harness code to write.
- **Argument validation** — ~~`validateToolCall(tools, toolCall)` is built
  in.~~ **WRONG — corrected 2026-08-04.** `validateToolCall` exists in
  pi-ai but is *called from nowhere inside it* (grep returns only the
  declaration and the definition). It is a utility for applications to
  invoke, not part of `complete()`/`stream()`.

  Consequence: without the harness calling it, raw model-supplied
  arguments reach handlers unchecked — a missing required field surfaces
  as whatever the handler happens to throw, and a tolerant handler
  proceeds on garbage with `isError: false`. `dispatchToolCall` now calls
  `validateToolArguments` before execution. The failure *shape* described
  above was right; the claim that pi-ai applied it was not.

So the actual scope is narrower than the original 3-day estimate:
`dispatchToolCall` itself, plus a registry `pi-ai` has no concept of.

## Decisions — locked in with the user, 2026-07-28

**1. Tool name → handler mapping lives in a separate `ToolRegistry`.**
Not folded into `ConversationManager` (message state only) or `pi-ai`'s
`Tool` (schema only, no execution function — `pi-ai` has no opinion on
how a tool actually runs). The registry does two jobs: produces the
`Tool[]` list for `Context.tools` (definitions only, no handlers leak
into what gets sent to the model), and gives `dispatchToolCall` something
to look up by name.

**2. `dispatchToolCall` auto-wraps thrown errors into an `isError`
result.** A handler throwing doesn't propagate — it becomes
`{ role: "toolResult", isError: true, content: [...] }`, the same failure
shape `pi-ai`'s own built-in argument-validation errors already use. One
consistent behavior for "bad arguments" and "handler crashed," rather
than two different failure modes a caller has to distinguish.

**3. Multiple tool calls in one turn run in parallel, via
`Promise.allSettled`.** Not `Promise.all` specifically — one tool call
failing must not lose the results of the others that succeeded in the
same turn. Each settled outcome maps independently to its own
`ToolResultMessage` (success or `isError`).

**4. `dispatchToolCall` is decoupled from `ConversationManager`.** It
returns `ToolResultMessage[]`, it does not import or reach into a
`ConversationManager` to append them. A separate orchestration loop
(not designed yet — likely 1.7's territory, or whatever eventually runs
the full request/response/tool-call cycle) is responsible for wiring
dispatch output into `append()`. Keeps both pieces independently
testable: `dispatchToolCall` can be tested with a fake registry and no
conversation state at all.

## Shape

```typescript
import type { Tool, ToolCall, ToolResultMessage } from "@earendil-works/pi-ai";

interface ToolHandler {
  definition: Tool;
  execute(args: Record<string, unknown>): Promise<{
    content: ToolResultMessage["content"];
    isError?: boolean;
  }>;
}

class ToolRegistry {
  private handlers = new Map<string, ToolHandler>();

  register(handler: ToolHandler): void {
    this.handlers.set(handler.definition.name, handler);
  }

  getToolDefinitions(): Tool[] {
    return [...this.handlers.values()].map((h) => h.definition);
  }

  get(name: string): ToolHandler | undefined {
    return this.handlers.get(name);
  }
}

async function dispatchToolCall(
  toolCall: ToolCall,
  registry: ToolRegistry,
): Promise<ToolResultMessage> {
  const handler = registry.get(toolCall.name);
  if (!handler) {
    return {
      role: "toolResult",
      toolCallId: toolCall.id,
      toolName: toolCall.name,
      content: [{ type: "text", text: `Unknown tool: ${toolCall.name}` }],
      isError: true,
      timestamp: Date.now(),
    };
  }
  try {
    const result = await handler.execute(toolCall.arguments);
    return {
      role: "toolResult",
      toolCallId: toolCall.id,
      toolName: toolCall.name,
      content: result.content,
      isError: result.isError ?? false,
      timestamp: Date.now(),
    };
  } catch (error) {
    return {
      role: "toolResult",
      toolCallId: toolCall.id,
      toolName: toolCall.name,
      content: [{ type: "text", text: error instanceof Error ? error.message : String(error) }],
      isError: true,
      timestamp: Date.now(),
    };
  }
}

async function dispatchToolCalls(
  toolCalls: ToolCall[],
  registry: ToolRegistry,
): Promise<ToolResultMessage[]> {
  const settled = await Promise.allSettled(
    toolCalls.map((call) => dispatchToolCall(call, registry)),
  );
  // dispatchToolCall itself never rejects (errors are caught internally),
  // so every settled result is "fulfilled" — allSettled here is really
  // about isolating each call's own try/catch, not about handling
  // rejection at this layer. Kept for defense in depth.
  return settled.map((s, i) =>
    s.status === "fulfilled"
      ? s.value
      : {
          role: "toolResult",
          toolCallId: toolCalls[i].id,
          toolName: toolCalls[i].name,
          content: [{ type: "text", text: "Unexpected dispatch failure" }],
          isError: true,
          timestamp: Date.now(),
        },
  );
}
```

Note: since `dispatchToolCall` already catches everything internally
(decision 2), `Promise.allSettled` mostly can't actually see a rejection
in practice — but it's kept anyway as defense in depth against a bug in
`dispatchToolCall` itself, rather than relying entirely on the inner
try/catch never being wrong.

## Where this connects to 1.5

Validated the "decoupled" decision (#4) against how the orchestration
loop would actually use both pieces together — the pattern is exactly
`pi-ai`'s own README example: get an `AssistantMessage` back, filter its
`content` for `ToolCall` blocks, call `dispatchToolCalls`, then
`conversationManager.append()` each `ToolResultMessage` one at a time.
Appending through `ConversationManager.append()` (not pushing directly
into `context.messages`) is what actually applies 1.5's
`maxToolResultChars` cap — so the decoupling doesn't lose that
enforcement, it just moves where it happens to the orchestration loop
instead of inside `dispatchToolCall`.
