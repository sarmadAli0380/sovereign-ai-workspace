# 1.7 — Integration proof and where the harness actually fits

**Status:** Complete, 2026-08-05 (reframed with the user 2026-07-30)
**Depends on:** 1.2, 1.4, 1.5, 1.6 — all implemented
**Supersedes:** the "refactor the Pi agent project" framing in
`phase1-model-agnostic-harness-expanded.md`

## The original framing doesn't survive contact with the target

1.7 was specified as: refactor a real project onto the harness, remove its
direct provider API calls, and demonstrate a provider swap via one config
edit. The named target was "the Pi agent project" — `local-pi`, at
`~/Documents/local-pi`.

`CLAUDE.md` already flagged this as suspect. Checking the target settles
it. Three findings, measured rather than assumed:

**1. There are no direct provider API calls to remove — zero.**
`local-pi/package.json` depends on `@earendil-works/pi-coding-agent`
^0.80.2 and no provider SDK. Grepping `src/`, `apps/` and `test/` for
`api.anthropic.com`, `api.openai.com`, `from "openai"`,
`from "@anthropic-ai/..."`, `ANTHROPIC_API_KEY` and `OPENAI_API_KEY`
returns nothing. Exactly two files import from `@earendil-works` at all:
`apps/pi-orchestrator/src/agentRunner.ts` and `oauthLogin.ts`.

**2. `local-pi` sits above this harness, not beside it.** `agentRunner.ts`
builds a full agent session:

```typescript
const authStorage = AuthStorage.create(authFile);
const modelRegistry = ModelRegistry.create(authStorage);
const { session } = await createAgentSession({
  authStorage, modelRegistry, agentDir,
  sessionManager: SessionManager.inMemory(),
});
session.subscribe(...);
await session.prompt(text);
await session.agent.waitForIdle();
```

`pi-coding-agent` supplies session management (which supersedes 1.5's
`ConversationManager`), an agent loop with built-in tools (which
supersedes 1.6's `ToolRegistry` + dispatch), and model/auth resolution
(which supersedes 1.4's `loadModel()` + credential store). Every piece the
harness owns already exists there in a more capable form.

**3. The provider swap is already a one-line config edit.**
`local-pi/agent-home/settings.json` carries `"defaultModel": "gpt-5.5"`.
Swapping models there is already config-driven — via `pi-coding-agent`'s
settings, not the harness's.

So a refactor would remove zero provider code, replace working components
with simpler ones, and re-demonstrate a capability the target already has.
It would make `local-pi` worse. **Decision with the user: don't do it.**

## What 1.7 is instead

Two deliverables, both honest about what they prove.

**A. The live swap proof** — `scripts/verify-swap.ts`. This is also 1.4's
outstanding definition of done ("run a script twice, editing only
`model.config.json` between runs, confirm identical `AssistantMessage`
shape"). It sends one prompt through two config keys with byte-identical
calling code and diffs the responses structurally — field presence and
types, never wording. It reports explicitly whether the two keys resolved
to different *providers* or merely different *models*, so a model swap
can't be quietly presented as a provider swap.

**B. This comparison** — the section below, which is the actual
intellectual content the "before/after" was reaching for.

## Where each layer fits

The harness and `pi-coding-agent` are not competitors at the same level.
`pi-coding-agent` is built on `pi-ai`; so is this harness. They are
siblings at different altitudes.

| | This harness (on `pi-ai`) | `pi-coding-agent` |
|---|---|---|
| Unit of work | One model call, or a short tool loop you drive | An autonomous agent session |
| Who owns the loop | Your application | The framework |
| Conversation state | `ConversationManager`, explicit `append()` | `SessionManager`, implicit |
| Tools | Only what you register | Built-in file/bash/edit suite + extensions |
| Control over context | Total — your truncation strategy, your budget | Framework's compaction |
| Auth | Config + `CredentialStore` you inject | `AuthStorage` |
| Right when | You need a model call *inside* an app, with predictable cost and no surprise tool use | You want an agent that works a task until done |

The harness's value is **subtraction**: it gives you a model call with
nothing attached — no agent deciding to read your filesystem, no
conversation growing where you can't see it, no tools you didn't
register. That is exactly wrong for a coding agent and exactly right for,
say, classifying a support ticket inside a request handler.

Read the other way: `local-pi` chose correctly. It wants an agent. Putting
this harness underneath it would mean rebuilding the agent loop by hand.

## What this means for the roadmap

The original framing assumed the harness's value was *replacing* provider
SDK calls. Against a codebase already on `pi-ai`, that value is zero — and
`local-pi` is the second time in this project that a task shrank on
contact with what `pi-ai` already provides (see 1.2, 1.3 and 1.6, all of
which lost most of their scope the same way).

The durable value is narrower and worth stating plainly:

- **Config-driven routing** as an application-level concern, decoupled
  from any agent framework's settings file.
- **Explicit context control** — a truncation strategy you choose, with a
  budget you can assert against in a test.
- **Tool dispatch without an agent** — parallel execution, error wrapping,
  and no framework deciding when to call something.

That is a real library. It just isn't a replacement for the layer above
it, and Phase 1's remaining honesty is in not claiming otherwise.

## Definition of done (revised)

- [x] Refactor target investigated and the original framing retired, with
      evidence (above).
- [x] `scripts/verify-swap.ts` written — structural diff across two config
      keys, provider-vs-model swap distinguished.
- [x] Comparison written (this file).
- [x] Swap proof **run against a real provider** — done, 2026-08-03.
      `openai-codex`, 22 fields compared, every required field present with
      matching types, zero code changes between runs. As predicted this is
      a *model* swap (`gpt-5.6-luna` ↔ `gpt-5.5`) and the script says so in
      its own output rather than letting it read as a provider swap.
- [x] Full request → tool-call → dispatch → response cycle exercised live
      (`verify-live.ts`): `toolUse` → `get_weather` dispatched →
      `stop` with the tool's answer used. Real usage numbers both turns.
- [x] **Genuine cross-provider swap** — done 2026-08-05, once Phase 2
      supplied the second leg. `verify-swap.ts codex-default local-qwen`
      reports *"providers: openai-codex vs ollama — genuine provider
      swap"*, 22 fields compared, zero code changes between runs. This is
      the real thing rather than the model-swap the 2026-08-03 run could
      only manage: two different API protocols (`openai-codex-responses`
      vs `openai-completions`), one hosted and one self-hosted.
- [x] **`step()` — the missing composition piece**, added 2026-08-05.
      Everything needed to drive a request → tool-call → response cycle
      existed after 1.6 *except* the piece that puts them together, so both
      verify scripts hand-rolled it and nobody could use the library
      without copying from a test.

      Deliberately **one transition, not a loop**: it performs exactly one
      model call, dispatches any requested tools, appends the results, and
      returns. The caller writes its own iteration. The distinction is who
      decides when to stop — an agent loop decides, this does not, so the
      stopping rule and turn cap stay visible in application code. That
      preserves the "value is subtraction" position argued above rather
      than drifting toward the layer this ADR declined to compete with.

      It is also the component `validate-context.ts` names as "the
      orchestration loop": the single place that converts a throw into a
      `HarnessResult` with `stopReason: "error"`. That contract was
      described in three files and implemented nowhere — `errorResult` had
      no caller outside its own test. `verify-live.ts` now drives its turns
      through `step()`, with the turn cap in the script.

Three corrections came out of running this rather than designing it —
`temperature` unsupported on codex, WebSocket transport blocked, and a
false pass in the verification script itself. All three are in
`findings-log.md`; the first changed 1.4's config schema.
