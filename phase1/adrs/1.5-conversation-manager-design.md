# 1.5 — ConversationManager design

**Status:** Decided with the user (research/design stage — no code yet)
**Depends on:** `1.2-schema-ontology-mapping.md` (message types), `1.4-config-routing-design.md` (where `contextWindow` comes from)

## Why this one isn't reframed by `pi-ai`

Unlike 1.2–1.4, this task doesn't shrink once you adopt `pi-ai`. `pi-ai`'s
`Context` type (`systemPrompt` + `messages` + `tools`) is plain data with
no behavior — no `append`, no truncation, nothing. Managing it over time is
genuinely the harness's job.

## Research: how production harnesses actually do this

Before designing anything, looked at how this problem is solved elsewhere,
specifically:

**`pi-coding-agent`** (the sibling package to `pi-ai`, same repo, same
team) has a fully worked implementation — "compaction," not just
truncation:
- Trigger: `contextTokens > contextWindow - reserveTokens` (default
  reserve: 16,384 tokens).
- Keeps the newest `keepRecentTokens` (default 20,000) verbatim; older
  content gets LLM-summarized into a structured note (Goal / Progress /
  Decisions / Next Steps) and spliced in as a synthetic message.
- Token counting is a chars/4 heuristic per message type — no tokenizer
  dependency, deliberately conservative (overestimates).
- Hard rule: never cuts at a tool result — valid cut points are only
  user/assistant/custom message boundaries, so a `ToolResultMessage`
  never survives without the `AssistantMessage` holding its `ToolCall`.

**Cross-harness survey (Arize, comparing Pi, OpenClaw, Claude Code,
Letta)** confirmed pi's numbers are the converged/median approach, not an
outlier, and surfaced a pattern all four independently arrived at that we
hadn't planned for: **tool-result size is capped separately from, and
before, whole-conversation compaction.** Claude Code caps at 50k chars/tool
(200k aggregate), OpenClaw at 16k chars or 30% of context, Letta clamps to
5k under pressure. Rationale given across all of them: tool results (file
reads, search, bash output) are consistently the single biggest
contributor to context bloat — bigger than the conversation text itself.
Every harness also keeps a dumb, guaranteed-to-work fallback under its
smart compaction (e.g. Claude Code deterministically head-drops the oldest
20% if the compaction call itself would overflow).

## Decisions — locked in with the user, 2026-07-28

Four open questions from the brainstorm, decided together rather than by
default:

**1. Tool-result capping is in scope for 1.5, not deferred.** A
`maxToolResultChars` cap applies to `ToolResultMessage.content` at append
time — separate from, and prior to, whole-conversation truncation.
Justification: every harness surveyed does this, it's cheap, and it
addresses the actual biggest contributor to bloat rather than only the
conversation-level symptom.

**2. Truncation is a pluggable strategy, shipped with drop-oldest as the
default.** Not "simple sliding window only" (the original spec's literal
words) — a strategy interface with drop-oldest as the Phase 1
implementation, so summarization can be swapped in later (per the
n-gram-based extractive idea flagged earlier, or LLM summarization like
`pi-coding-agent`'s) without redesigning `ConversationManager` itself.

**3. `ConversationManager` is a stateful class wrapping one `Context`.**
Exposes `append()`/`getHistory()`/`truncateToFit()` per the original
spec's method names. Matches `pi-ai`'s own framing of `Context` as
serializable state meant to be held and persisted (JSON in, JSON out),
not just a call parameter.

**4. Truncation runs on every `append()`, not lazily before a call.** The
`Context` is always within budget; nothing can be built up and then blow
the window right when a call is about to go out.

## Shape

```typescript
import type { Context, Message, ToolResultMessage } from "@earendil-works/pi-ai";

interface TruncationStrategy {
  /** Returns a trimmed message list that fits within `budgetTokens`.
   *  Must never separate a ToolCall from its ToolResultMessage. */
  truncate(messages: Message[], budgetTokens: number): Message[];
}

interface ConversationManagerOptions {
  systemPrompt?: string;
  tools?: Context["tools"];
  contextWindow: number;   // from the resolved Model (1.4's loadModel())
  reserveTokens?: number;  // default TBD, pi-coding-agent uses 16384
  maxToolResultChars?: number; // default TBD
  strategy?: TruncationStrategy; // default: drop-oldest
}

class ConversationManager {
  private context: Context;
  private budget: number; // contextWindow - reserveTokens
  private maxToolResultChars: number;
  private strategy: TruncationStrategy;

  constructor(options: ConversationManagerOptions) { /* ... */ }

  append(message: Message): void {
    if (message.role === "toolResult") {
      message = capToolResult(message as ToolResultMessage, this.maxToolResultChars);
    }
    this.context.messages.push(message);
    this.context.messages = this.strategy.truncate(this.context.messages, this.budget);
  }

  getHistory(): readonly Message[] {
    return this.context.messages;
  }

  getContext(): Context {
    return this.context; // what actually gets passed to pi-ai's complete()/stream()
  }
}

const dropOldestStrategy: TruncationStrategy = {
  truncate(messages, budgetTokens) {
    // Walk backwards accumulating a chars/4 token estimate per message
    // (same heuristic as pi-coding-agent). Cut only at user/assistant
    // message boundaries so tool-call/result pairs stay atomic. Always
    // keep the most recent messages; drop from the front.
    // (Full algorithm not written yet — this is the contract, not the impl.)
  },
};
```

## Open items, deliberately left for implementation time

- **Actual default values** for `reserveTokens` and `maxToolResultChars`
  aren't picked yet — `pi-coding-agent`'s numbers (16,384 / no direct
  tool-result equivalent since it caps at summarization time, not append
  time) are a reference point, not something to copy blindly without our
  own usage data. Revisit once there's a real conversation to test
  against.
- **`dropOldestStrategy`'s exact cut-point algorithm** — the contract
  (never split a tool-call/result pair, walk backwards from newest) is
  decided; the implementation isn't written.
- **Forward-looking, not in scope now:** n-gram-based extractive
  summarization or dedup as a future `TruncationStrategy` implementation,
  swapped in without touching `ConversationManager` itself, per the
  earlier throwaway-question discussion.

## A second axis for choosing a strategy: prefix stability (added 2026-08-05)

Strategy choice was framed here purely as *what to keep*. There is a second
consequence nobody accounted for: **a truncation strategy decides whether
prompt caching can work at all.**

Prompt caching — OpenAI's, Anthropic's, and llama.cpp's own — keys on an
**identical prefix**. OpenAI's guidance is explicit: static content first,
variable content last, and the prefix must match byte for byte, with a
1,024-token floor before any caching engages. Anthropic's `cache_control`
markers and llama.cpp's slot-level prompt cache differ in mechanism and
agree on that requirement.

`dropOldestStrategy` removes messages from the **front** of the list. That
is precisely the region caching needs held constant, so every eviction
invalidates the cached prefix beyond the point where the messages begin.

It is not fatal, and the reason is structural rather than lucky:
`systemPrompt` and `tools` live on the `Context` as sibling fields, not in
`messages`, so they are never truncatable and stay byte-identical across a
whole conversation. Providers hash roughly the first 256 tokens for
routing, so that part keeps hitting. What is lost is the *extent* — the
cached prefix collapses back to the end of the tool schemas on every
eviction, instead of growing with the conversation.

**This does not change the default.** Drop-oldest remains right for the
reasons already recorded, and at the prompt sizes this project actually
runs (131–950 tokens measured across both providers) caching never engages,
so there is nothing to lose today. It is recorded because it changes how a
*replacement* strategy should be judged: a summarise-and-keep-prefix
strategy is not merely "keeps more meaning", it is the one that keeps the
cache alive, and that is a second reason to prefer it that this ADR's
framing would otherwise miss.

`findings-log.md` for the measurement that prompted this.
