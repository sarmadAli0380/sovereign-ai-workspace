# 1.8 — Token budgeting: anchoring on measured input

**Status:** Decided from measurement, pre-implementation (2026-08-05)
**Depends on:** 1.5 (ConversationManager owns truncation), 1.2 (`Usage` is
already carried on `AssistantMessage` and surfaced by `HarnessResult`)
**Supersedes:** the framing in `SESSION-HANDOFF.md` that called this
"transcription, not design"

## How to read this document

Same convention as 2.4/2.5. **[VERIFIED]** means measured against a live
provider with the evidence inline; **[UNVERIFIED]** means believed but not
proven; an unmarked statement is a decision rather than a claim about the
world.

## Why this was reopened

The handoff described one defect: `ConversationManager` re-estimates the
whole conversation on every `append()` with a chars/3 heuristic measured to
underestimate code by ~1.37×, while `AssistantMessage.usage` already
carries the provider's real count and throws it away. The fix was described
as settled — anchor on the reported count, estimate only the delta — and
therefore mechanical.

Two questions were left open, and answering them properly required
measurement rather than reasoning:

- **A.** What to do when a provider reports no usage at all.
- **B.** Whether `openai-codex`, already proven to silently ignore
  `maxTokens`, reports usage that can be trusted.

Probing those turned up a **second, independent defect** and disproved the
obvious form of the fix. Both are recorded below.

## Defect 1: the budget is blind to most of what is sent

**[VERIFIED]** `ConversationManager.getEstimatedTokens()` calls
`estimateContextTokens(this.context.messages)`
(`conversation-manager.ts:198`), and `dropOldestStrategy` truncates over the
same message list. But the constructor stores `systemPrompt` and `tools` as
sibling fields on the `Context` (`conversation-manager.ts:162`), and **both
are sent on every single request**. Neither is ever counted — not by the
budget check, not by the truncation decision.

Measured with the `get_weather` round trip in `scripts/verify-live.ts`,
whose entire message list at turn 1 is one 23-token user string:

| | estimator sees | provider reported |
|---|---|---|
| `codex-default` turn-1 input | 23 | **82** |
| `local-qwen` turn-1 input | 23 | **153** |

Decomposing the codex number: the system prompt is 62 characters (≈21
tokens at chars/3) and one trivial tool schema accounts for the remaining
≈38. A second probe with **no tools registered** and a 27-character system
prompt reported an input of 74 against a 57-token user message plus ≈9
tokens of system prompt — a residual of only ≈8 for protocol scaffolding.

**So the estimator itself is roughly accurate on prose. The bug is
coverage, not arithmetic.** One trivial tool costs ~38 invisible tokens; a
real agent carries fifteen to twenty schemas, which is thousands of tokens
the budget never sees — and turn 1, the turn most exposed to this, is
precisely the turn no usage anchor can ever help with, because no response
has come back yet.

**Decision: count `context.systemPrompt` and `context.tools` in
`estimateContextTokens`, and land it before the anchor.** It is provider
independent, strictly correct, and it gives the anchor work a baseline that
is wrong in only one way instead of two.

## Defect 2: an assistant turn's replay cost is not what the harness holds

This is the finding that invalidated the obvious fix.

Two three-turn probes, identical prompts, chosen to force heavy reasoning
behind a one-word answer so that visible output is ~0 and any large
`output` must be reasoning.

**[VERIFIED]** `codex-default` (`gpt-5.6-luna`), no tools:

| turn | in | out | cacheRead | cacheWrite | blocks | thinking chars | text chars |
|---|---|---|---|---|---|---|---|
| 1 | 74 | 58 | 0 | 0 | thinking, text | **0** | 8 |
| 2 | 172 | 50 | 0 | 0 | thinking, text | **0** | 8 |
| 3 | 248 | 23 | 0 | 0 | thinking, text | **0** | 2 |

**[VERIFIED]** `local-qwen` (`qwen3:4b`), same prompts:

| turn | in | out | cacheRead | cacheWrite | blocks | thinking chars | text chars |
|---|---|---|---|---|---|---|---|
| 1 | 75 | **1261** | 0 | 0 | thinking, text | 3106 | 5 |
| 2 | 125 | **1880** | 0 | 0 | thinking, text | 4930 | 5 |
| 3 | 160 | **1164** | 0 | 0 | thinking, text | 3403 | 2 |

Read those two tables together and the harness's model of a conversation
falls apart in **opposite directions**:

- **Codex emits a `thinking` block with zero characters of `thinking`.** The
  harness's record of that assistant turn is ~3 tokens of visible text,
  while the provider's input grows ~37 tokens per turn more than that
  explains. The harness's record **understates** the wire cost.

  **CORRECTION (2026-08-05, QA pass):** this originally read "replaying
  reasoning the harness cannot see and cannot measure." That is wrong. The
  payload is in `thinkingSignature` — measured at 1146 characters on one
  turn — and pi-ai sends it straight back to the provider
  (`openai-responses-shared.js:139`). `estimateTokens` simply was not
  counting that field, scoring the whole message at 5 tokens. The cause was
  an uncounted field, not an invisible one, and the ~37 tokens/turn had a
  mundane explanation all along. Fixed; see `findings-log.md`.
- **Qwen emits 3106 characters of thinking, which `estimateTokens` counts**
  (`truncation.ts`, the `thinking` case adds `block.thinking.length`) — so
  the harness records that turn as ≈1039 tokens. The next request's input
  grew from 75 to 125. The thinking was **not replayed at all**. The
  harness's record **overstates** the wire cost by roughly 9×.

**[VERIFIED]** reasoning tokens *are* counted in `usage.output` on both
providers — codex reported 58 output tokens for an 8-character answer, qwen
reported 1261 for a 5-character one. That closes Decision B's main open
risk, but it does so in a way that makes `output` useless as a predictor:
output is real, and its replay is not.

**[UNVERIFIED]** replay appears to depend on message *shape*, not just
provider. The earlier `verify-live` tool round trip on the same qwen model
showed turn-2 input of 396 against a turn-1 total of 376 — consistent with
the whole assistant turn including thinking being replayed, the opposite of
this probe. The plausible mechanism is that reasoning is preserved across a
tool-call continuation and dropped once a user message closes the turn.
Observed, not characterised; do not rely on it.

An earlier note in this project's chat inferred from that single
tool-calling data point that qwen replays thinking. This probe disproves it
for the plain-text case. The inference was flagged at the time as resting on
an arithmetic coincidence, and it was.

## What this means for the anchor

The purpose of the budget is to predict **the size of the next request's
input**. Three candidate rules, evaluated against both probes:

### A1 — anchor on `prev.in + prev.out`, add new user messages

The obvious reading of the Codex-hybrid design.

| | predicted | actual | error |
|---|---|---|---|
| codex 1→2 | 189 | 172 | +17 (safe) |
| codex 2→3 | 259 | 248 | +11 (safe) |
| qwen 1→2 | 1393 | 125 | **+1268 (11×)** |
| qwen 2→3 | 2042 | 160 | **+1882 (13×)** |

Never unsafe, and unusable. On an 8192-token window with a 6144 budget, a
phantom 1.3–1.9k tokens per turn would have the harness truncating a
conversation the server sees as 160 tokens. **Rejected.**

### A2 — anchor on `prev.in`, estimate the delta from message content

Anchor is `{ tokens: usage.input, messageCount }` recorded at the moment a
request is sent; the budget is `anchor.tokens + estimate(messages appended
since)`.

| | predicted | actual | error |
|---|---|---|---|
| codex 1→2 | 134 | 172 | −38 (understates) |
| codex 2→3 | 212 | 248 | −36 (understates) |
| qwen 1→2 | 1171 | 125 | +1046 (overstates) |
| qwen 2→3 | 1810 | 160 | +1650 (overstates) |

Still visibly wrong per turn — but with a property A1 lacks and today's code
lacks: **the error cannot compound.** Every turn re-anchors on a freshly
measured `input`, so a prediction is wrong by at most *one* turn's replay
delta, and the next turn starts from truth again.

Contrast with the status quo, which estimates the whole history: on the qwen
probe today's code would report ≈2838 tokens at turn 3 against a real input
of 160, and that gap widens with every turn until it truncates a
conversation the server considers trivial. **That unbounded drift is the
actual defect, and A2 is what fixes it** — not the per-turn accuracy, which
stays mediocre.

### A3 — A2 plus a self-calibrating residual

Carry forward the last observed prediction error and apply it as a
correction. On codex it converges to roughly +37/turn; on qwen it is a large
negative. It needs no provider names — the coefficient is learned at
runtime, which fits this project's "provider quirks are data, not code"
rule better than a config flag would.

**Decision: implement A2. Note A3 as a refinement, do not build it yet.**
A2 already removes the unbounded drift, which is the whole point; A3 buys
per-turn sharpness at the cost of state that is harder to reason about, and
there is no measurement yet showing the sharpness matters.

## Decision A — when a provider reports no usage

**Rejected: a per-provider config flag** (`usageReported: false`). It fits
the sanctioned pattern used for `transport`, `maxTokensHonored` and
`contextWindow`, but those declare things that are *invisible in the
response* and can only be established by a deliberate probe. Usage presence
is observable in the response already in hand. Declaring what you can
observe is strictly worse: it can be stale, it must be maintained per
provider, and — decisively — usage absence is **not a provider property at
all**.

The evidence for that last point comes from `odysseus-dev/odysseus`, whose
`tests/test_llm_core_usage_finish_delta.py` documents a shipped bug where
usage arriving on a non-empty finish delta was silently dropped, so affected
providers' accounting read zero. Their other cases cover a null `usage`
field and null heartbeat chunks. **Absence of usage is a per-response,
transport-dependent event.** A provider that reports on ninety-nine calls
can report nothing on the hundredth.

**Decision:**

1. **Per-response, not per-provider.** A response either carries a usable
   usage or it does not.
2. **A silent response does not reset anything — the anchor simply does not
   advance**, and the delta window widens to cover the un-anchored span.
   Error then grows gradually with the gap rather than snapping back to
   whole-history error. With no anchor ever recorded, behaviour degrades to
   today's pure heuristic, which is the correct floor.
3. **Treat present-but-zero as absent.** A zero input on a non-empty request
   is not a measurement. Odysseus arrived at the same rule independently —
   they emit a usage event only when input or output is non-zero.
4. **Truncation invalidates the anchor.** Dropped messages were counted in
   it. Reducing it correctly is fiddly and easy to get subtly wrong;
   invalidating is conservative and self-healing, because the next response
   re-anchors.
5. **Track provenance.** Whether the current number is anchored or estimated
   must be visible to callers, not buried. This is the project's
   "separate decisions from facts" agreement applied to a runtime value, and
   it is what makes the anchor's accuracy measurable in a live run rather
   than assumed.

Point 5 has a direct precedent in the same repository:
`budget_context_for_model()` in `src/model_context.py` returns a context
window only when it was actually discovered and returns 0 otherwise so that
auto-scaling stays conservative, with a comment to the effect that a
fallback 128K is not proof a model holds 128K. That is this project's own
"providers lie about their context window" finding, reached independently,
and it is the same discipline: **bind a number to the evidence for it.**

## Decision B — is `openai-codex`'s usage trustworthy?

**[VERIFIED] Yes, for this purpose.** Across six live turns it reported
present, numeric, internally consistent counts (`total` equalled
`input + output` in every case), it grew monotonically with the
conversation, and it **does count reasoning tokens in `output`** — 58 output
tokens for an 8-character answer. `verify-live`'s shape conformance check
passes on `usage.input`, `usage.output`, `usage.totalTokens` and
`usage.cost.total`.

The reasoning worth **not** carrying forward: *codex ignores `maxTokens`,
therefore codex misreports usage.* Mishandling a request parameter and
misreporting a response field are different failure modes. The prior for
scrutiny is raised; the conclusion is not implied. Independent corroboration
that this surface is unusual — odysseus's Responses payload builder notes
that the ChatGPT subscription endpoint rejects `max_output_tokens` outright
with an HTTP 400, where ours accepts and ignores — sharpened the question
without answering it. Only the probe answered it.

**Decision: trust it, and keep the design tolerant of it being wrong**, on
the grounds that the choice is asymmetric. Today the harness believes the
`verify-live` conversation is 66 tokens where codex says ~131. A usage
number wrong by 20% is a large improvement on a 2× underestimate. The
reserve and truncation remain the actual safety net; the anchor is an
accuracy improvement, not a guarantee.

## Open items

- **[Was a defect, now fixed]** `cacheRead`/`cacheWrite` were 0 on every
  probe turn, so the sum shipped unexercised. A QA pass then found the gate
  in front of it tested `usage.input <= 0` while the value taken was
  `input + cacheRead + cacheWrite` — so a fully cached prefix
  (`input: 0, cacheRead: 8000`, which is exactly how pi-ai normalises
  OpenAI usage: `input = max(0, prompt_tokens − cacheRead − cacheWrite)`)
  threw the measurement away *precisely when caching works*. The gate now
  tests the sum. Behaviour against a genuinely caching provider is still
  unobserved.
- **[UNVERIFIED]** the shape-dependence of reasoning replay (tool-call
  continuation vs completed turn) is observed on qwen but not characterised.
- The chars/3 constant stays as it is. These probes show it is close on
  prose; the coverage fixes matter far more than the constant, and 1.5
  already records it as a tunable with data behind it.

## Definition of done

- [x] `systemPrompt` and `tools` counted — landed first, independently, as
      `estimateOverheadTokens()`. Charged as a fixed floor off the budget
      rather than handed to truncation, since no strategy can drop a tool
      the caller registered. **[VERIFIED]** live: the `verify-live`
      conversation that estimated 66 tokens against codex's reported ~131
      now estimates 151 — from 2.0× under to 1.15× over, i.e. into the safe
      direction the heuristic's contract calls for.
- [x] Anchor recorded per response as `{ tokens, messageIndex }`, advanced
      only on a usable usage (zero input counts as absent), invalidated by
      truncation, never cleared by a silent response.
- [x] Budget computed as anchor plus delta, with provenance exposed via
      `getBudgetUsage(): { tokens, source }`. The truncation strategy
      interface is untouched — 1.5's contract holds — because the anchor is
      applied by *shifting the budget handed to the strategy* rather than by
      teaching strategies about anchors:
      `allowed = budget − anchor.tokens + heuristic(anchored prefix)`,
      which reduces exactly to `heuristic(suffix) <= budget − anchor.tokens`.
- [x] A live run prints anchored vs pure-heuristic side by side.
      **[VERIFIED]** on both providers, same `verify-live` conversation:

      | | anchored | pure heuristic | provider truth |
      |---|---|---|---|
      | codex | **131** | 151 | 131 |
      | ollama | **730** | 748 | 611 |

      Codex lands exactly on the reported figure. Both stay on the
      overestimating side, which is the direction the heuristic's contract
      asks for.
- [x] Decision A resolved: per-response with a stale anchor, not a config
      flag.
- [x] Decision B resolved: codex usage verified, including reasoning tokens.
- [ ] Cache-reporting behaviour verified against a caching provider.
