# Spike: `pi-ai` vs. LiteLLM proxy — same test, both ways

Built the same test case both ways: one tool (`get_weather`), two providers
(Anthropic + OpenAI), through each harness approach. Both reached the real
Anthropic API and got an identical `401 invalid x-api-key` response —
confirming both work correctly at the protocol level (OpenAI's endpoint
wasn't reachable from this sandbox's network rules, so that leg is untested
here — worth a quick retry with real keys in your own environment).

## What "Pi SDK" actually means here

Pi ships two relevant packages: `@earendil-works/pi-coding-agent` (the CLI
product) and `@earendil-works/pi-ai` (the unified LLM layer underneath it —
this is the piece that matters for the harness). `pi-ai` wraps the real
provider SDKs (`@anthropic-ai/sdk`, `openai`, `@google/genai`,
`@aws-sdk/client-bedrock-runtime`, `@mistralai/mistralai`) behind one typed
interface, rather than reimplementing HTTP calls itself.

## Setup

| | `pi-ai` | LiteLLM proxy |
|---|---|---|
| Install | 1 npm package | pip install (separate Python runtime) + a proxy process to run and supervise |
| Files needed | 1 TS file | `config.yaml` + a client file, in two different tools/languages |
| Process model | Runs in the same Node process as your app | Separate server on a port — needs starting, health-checking, restarting |
| Total code | 41 lines | 34 lines (client) + 9 lines (config) = 43 lines, split across the process boundary |

## Type safety

`pi-ai`'s `Context`/`Message`/`ToolCall`/`AssistantMessage` types are checked
by the TypeScript compiler end to end, including tool parameter schemas via
`typebox`. The LiteLLM proxy path is JSON over HTTP — no compile-time safety
on the wire; you'd hand-write or import types matching the OpenAI chat
completion shape yourself.

## Ties directly into 1.2

This is the part worth flagging on its own: `pi-ai`'s built-in types are
almost exactly the ontology sketched for 1.2 last session —

```typescript
interface ToolCall { type: "toolCall"; id: string; name: string; arguments: Record<string, any>; }
interface ToolResultMessage { role: "toolResult"; toolCallId: string; toolName: string; content: ...; }
type Message = UserMessage | AssistantMessage | ToolResultMessage;
interface AssistantMessage { role: "assistant"; content: ...; usage: Usage; stopReason: StopReason; ... }
```

Role-based messages, a `ToolCall` with `id`/`name`/`arguments`, a
`ToolResultMessage` that answers a call by id, a `Usage` object with token
and cost breakdown. Adopting `pi-ai` means 1.2 is largely already done
rather than built from scratch — you'd adapt these types instead of
inventing your own.

## Where LiteLLM still wins

The proxy's reason for existing — centralized spend tracking, per-client
virtual keys, load balancing across many keys/deployments, admin UI — maps
directly onto **Phase 5's multi-tenant requirements**. That's real, and it's
not something `pi-ai` is built for; it's a library for one app to call
models, not a service for a consulting firm to run centrally across clients.
It's just four phases away, not a Phase 1 concern.

## Ecosystem reality check

LiteLLM is large, established, and built specifically to solve this problem
at production scale. `pi-ai` is real and well-engineered, but younger and
narrower — its primary consumer today is the Pi coding agent itself, not
general app backends. That's a genuine adoption-risk tradeoff, offset by
already having hands-on experience with Pi's tool-calling behavior from the
CodeNinja agent project.

## Read

On this spike, `pi-ai` came out ahead for Phase 1 specifically: less code,
compiler-checked types, and an ontology that maps onto 1.2 almost directly,
in the language the harness was already going to be built in. LiteLLM's
strongest argument — the proxy's multi-tenant features — is a Phase 5
concern, and if it's needed later, LiteLLM's proxy can sit *behind* a
`pi-ai`-shaped harness as one more routing backend rather than as the
harness's public interface — the same relationship ADR-001 originally
proposed, just with the roles swapped.

**Recommendation:** revise ADR-001 to `pi-ai` as the translation layer for
1.3, keep the thin custom harness for 1.4–1.7, and revisit LiteLLM
specifically at Phase 5 if multi-tenant proxy features are actually needed
by then.
