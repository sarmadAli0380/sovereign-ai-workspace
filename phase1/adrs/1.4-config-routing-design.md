# 1.4 — Config-driven model routing, on `pi-ai`'s `Models` registry

**Status:** Decided (research/design stage — no code yet)
**Depends on:** ADR-002, `1.2-schema-ontology-mapping.md`, `1.3-provider-coverage-scope.md`

## A correction from researching this task

Digging into `pi-ai`'s actual source (`packages/ai/src/index.ts`,
`models.ts`, `providers/all.ts`, `compat.ts`) turned up something that
affects 1.2 and 1.3 too: the flat `getModel()` function the README's Quick
Start uses isn't exported from the root `@earendil-works/pi-ai` package —
root `index.ts` only exports `createModels()` / `createProvider()` and the
`Models`/`Provider` interfaces from `models.ts`. The flat `getModel()` /
`getModels()` only exist via the `/compat` subpath, and are explicitly
marked `@deprecated` there, with a comment saying new code should use
`createModels()` and the provider factories instead. The README's own
example is out of step with the library's current source.

Practical effect: 1.2 and 1.3's illustrations that called `getModel('openai',
...)` directly were following the README, not the more current pattern.
The concepts in both docs (which types get adopted, which providers need
no adapter code) hold regardless — but the actual call shape changes here,
in 1.4, since this is the task that decides how the harness resolves a
config key to a model in the first place.

## What `pi-ai` actually offers for this

Two integration levels, not one:

1. **Flat, standalone** — build a `Model<Api>` object by hand (the
   README's LiteLLM example does this), call `stream()`/`complete()`
   directly with an explicit `apiKey` in the call options. No registry, no
   env-based auth resolution — the caller supplies the key every time.
2. **Registered, via `Models`** — `createModels()` returns a `Models`
   collection; `setProvider()` registers `Provider` objects (built via
   `createProvider()`) into it. Once registered, `models.getModel(provider,
   id)` does the lookup, and `models.complete(model, context)` resolves
   auth automatically (env vars, OAuth, ambient credentials — whatever the
   provider's `ProviderAuth` declares) before calling the underlying API.
   `builtinModels()` (from `pi-ai`'s `providers/all.ts`) is a convenience
   that returns a `Models` collection pre-loaded with every built-in
   provider — Anthropic and OpenAI included, fully auth-wired already.

For the harness, option 2 is the better fit specifically because of 1.4's
own definition of done: "no branching logic in the caller." A single
`models.getModel(provider, id)` call handles native and gateway routing
identically once both are registered in the same collection — no
`if (routedVia === 'gateway')` branch needed at lookup time, unlike the
draft sketch in `1.3-provider-coverage-scope.md`. That draft becomes the
fallback structure only if registering the gateway model turns out not to
be worth the extra `ProviderAuth` wiring (see open item below).

## Config schema — decided with the user, 2026-07-28

Discussed as an explicit choice rather than defaulting into it: which
fields beyond `provider`/`modelId` earn a place in Phase 1's config file.
Decision: **keep it to `maxTokens` + `temperature` only.** Everything else
considered is deferred, not rejected outright — reasoning below so it
doesn't need re-litigating later.

```json
{
  "claude-default": {
    "provider": "anthropic",
    "modelId": "claude-sonnet-5",
    "maxTokens": 4096,
    "temperature": 0.7
  },
  "gpt-default": {
    "provider": "openai",
    "modelId": "gpt-5.6-luna",
    "maxTokens": 4096,
    "temperature": 0.7
  }
}
```

**Fields considered and deferred:**

- **`fallbackConfigKey`** — auto-retry against another configKey on
  failure. Real production behavior, but nothing in Phase 1 exercises
  failure modes yet; adding it now would be unused surface area. Revisit
  once there's an actual reliability requirement driving it.
- **`routedVia` (`native`/`gateway`)** — explicit audit tag for native vs.
  LiteLLM-gateway calls. Deferred along with the rest of the gateway path
  per ADR-002 (Phase 5, not Phase 1) — there's nothing to tag yet since no
  gateway provider is registered. Add it back when the gateway provider
  actually gets registered, not before.
- **`apiKeyEnv`** — rejected, not just deferred. `pi-ai`'s built-in
  providers already resolve auth from standard env vars
  (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, etc.) via `ProviderAuth` —
  naming them again in harness config would be a second place that can
  drift out of sync with zero benefit. Same shape of finding as 1.2's
  dropped `raw_provider_metadata` field.

**Consequence for `HarnessResult` (1.2):** the `routedVia` field on
`HarnessResult` doesn't have a config-level source yet. That's fine for
now — it's meaningless anyway while every entry is native-only. It gets a
real value once the gateway provider exists to route to.

## `loadModel()`

```typescript
import { builtinModels } from "@earendil-works/pi-ai";
import type { Model, Api } from "@earendil-works/pi-ai";

const models = builtinModels(); // Anthropic, OpenAI, etc. — auth already wired

interface ConfigEntry {
  provider: string;
  modelId: string;
  maxTokens: number;
  temperature: number;
}

function loadModel(
  configKey: string,
  config: Record<string, ConfigEntry>,
): { model: Model<Api>; entry: ConfigEntry } {
  const entry = config[configKey];
  if (!entry) throw new Error(`Unknown configKey: ${configKey}`);

  const model = models.getModel(entry.provider, entry.modelId);
  if (!model) throw new Error(`No model for ${entry.provider}/${entry.modelId}`);
  return { model, entry };
}
```

No fallback recursion and no `routedVia` branch — both deferred per the
schema decision above. `loadModel()` is a single lookup, which is exactly
what the original 1.4 spec's "no branching logic in the caller" asked
for, just simpler than the earlier draft since there's only one routing
path to support right now.

## Open item, still deferred: the gateway provider's `ProviderAuth`

`createProvider()` requires an `auth: ProviderAuth` — at minimum an
`ApiKeyAuth` with a `resolve()` function. The README's LiteLLM example
sidesteps this entirely by using the flat `stream()` call with an explicit
`apiKey` instead of registering a `Provider`. Registering it properly
raises a real question not yet answered: does the LiteLLM proxy need its
own master key (`resolve()` reads `LITELLM_MASTER_KEY` or similar), or is
local access assumed keyless in dev with real auth added later? Not
resolved here — deferred alongside the rest of the gateway-path
verification to Phase 5 per ADR-002, consistent with dropping
`routedVia` from config above.

## Correction from implementation, 2026-08-03: `temperature` is optional

Running this against `openai-codex` returned
`Codex error: Unsupported parameter: temperature`. The schema above treats
`temperature` as always present; it isn't universally supported, and pi-ai
has no compat flag that auto-detects it.

`ConfigEntry.temperature` is therefore **optional**, and omitted from the
request entirely when absent. Rejected alternative: deriving it from
`model.reasoning`, which would be right for codex and wrong for Anthropic
(whose reasoning models do accept temperature). See `findings-log.md`.

`transport` was also needed, and deliberately kept *out* of this schema —
it describes the network, not the model. It comes from `HARNESS_TRANSPORT`
instead, on the same reasoning that excluded `apiKeyEnv`.
