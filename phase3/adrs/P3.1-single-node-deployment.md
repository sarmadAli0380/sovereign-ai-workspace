# P3.1 — Supported topology and reproducible single-node deployment

**Status:** Accepted and implemented, 2026-08-24  
**Scope:** the first supported deployment substrate; not the Phase C HTTP/SSE
server or the Phase D web UI  
**Depends on:** B0 storage prerequisites and the B7 residency/recovery gate

**2026-08-25 extension:** C2 now supplies the real long-running server shown as
future in this ADR. It is the sole loopback-published ingress; PostgreSQL and
Ollama remain internal. `phaseC/adrs/C2-durable-run-command-gateway.md` owns
that extension without changing P3.1's original substrate decision.

## Context

The runtime and persistence layers are complete, but the repository previously
had no packaged way to reproduce their operational dependencies on a host the
developer does not administer. A Compose file alone would not be an adequate
decision: service ownership, egress, secrets, volume durability, readiness,
migrations, backups, and upgrade order all affect the sovereignty claim.

The product roadmap still requires a server plus web UI. This milestone does
not invent a placeholder server. It packages the runtime image and the real
PostgreSQL/Ollama dependencies, exposes one-shot operational jobs, and fails
readiness unless the implemented B-layer contracts are actually present.

## Decision 1 — one Linux host is the first supported topology

P3.1 supports one operator-owned Linux Docker host, on-premises or in a
client-controlled private cloud account. Docker Engine plus Compose owns the
process lifecycle. Multi-host scheduling, Kubernetes, managed databases,
managed model endpoints, and shared object storage are separate variants and
are not implied by this topology.

The steady-state graph is:

```text
                    internal Compose data_plane (no host ports, no gateway)

  future Phase C server  ─────> PostgreSQL 18 + pgvector 0.8.6
           │
           ├──────────────────> Ollama 0.32.5 + pinned qwen3:4b
           │
           ├──────────────────> attachments volume
           └──────────────────> encrypted event-spool volume

  one-shot jobs: migrations, volume initialization, readiness, backup
```

There is deliberately no long-running application service yet: Phase C must
provide the authenticated HTTP/SSE process. No database or inference port is
published to the host. The present Compose stack is a deployment substrate,
not a user-facing product release.

## Decision 2 — exact images and build inputs are pinned

All upstream images use both an exact tag and the multi-architecture manifest
digest resolved on 2026-08-24:

| Component | Pinned artifact |
|---|---|
| Node runtime | `node:24-bookworm-slim@sha256:3638…fc03` |
| PostgreSQL/pgvector | `pgvector/pgvector:0.8.6-pg18-bookworm@sha256:2ba9…7e7a` |
| Ollama | `ollama/ollama:0.32.5@sha256:4dea…2131` |
| dbmate | `ghcr.io/amacneil/dbmate:2.35.0@sha256:e550…7e0d` |

The runtime image uses `npm ci --omit=dev --ignore-scripts` against the tracked
lockfile. The migration image copies only the immutable checked migration
directory. The model is separately pinned to the full Qwen digest already
recorded by live conformance:
`sha256:359d7dd4bcdab3d86b87d73ac27966f4dbb9f5efdfcc75d34a8764a09474fae7`.
A mutable model tag cannot pass readiness if it resolves to another digest.

## Decision 3 — steady state is local-only; provisioning is explicit egress

`database`, `inference`, migrations, readiness, and backup attach only to an
`internal: true` data network. No service publishes a host port. Ollama runs
with cloud features disabled, one loaded model, one parallel sequence, and an
8,192-token context.

The only egress-capable workload is the `model-bootstrap` one-shot service,
which requires an explicit Compose profile. It downloads the model into the
persistent Ollama volume, verifies the digest prefix through Ollama, then
exits. The steady inference service never joins that network. An air-gapped
deployment must import the pinned OCI images and pre-populated model volume
through the client's controlled media process; `up-airgapped` performs no
pull, build, or bootstrap.

This follows Docker's documented `internal` network semantics and Ollama's
documented `OLLAMA_NO_CLOUD=1` local-only mode. Application-level exact-origin
egress denial from B7 remains a second, independent boundary.

## Decision 4 — secrets are files with least-privilege grants

Compose secrets mount a database password and a 256-bit event-spool key under
`/run/secrets`. Direct password/key environment variables fail configuration.
The database and migration/backup jobs receive only the database password;
the runtime readiness job receives both; inference receives neither.

dbmate and `pg_dump` use a mode-`0600` temporary `.pgpass`, so the password is
not placed in a URL, process argument, Compose environment, report, or image
layer. Secret encodings and regular-file/no-symlink requirements are validated
before use.

## Decision 5 — persistent state and ownership are explicit

Four named volumes survive ordinary `down`: PostgreSQL data (mounted at the
PostgreSQL-18 `/var/lib/postgresql` boundary), Ollama models, attachments, and
the encrypted event spool. A network-disabled, capability-minimized one-shot
job initializes the application volumes to UID/GID `1000:1000`, mode `0700`.
It refuses to change ownership of a non-empty volume it does not already own.

Backups are different: the one-shot backup job writes custom-format archives
and adjacent SHA-256 files to the operator-visible `deployment/backups` bind
mount. The platform operator owns the schedule, off-host replication,
35-day expiry, restore isolation, and alerting. Compose does not pretend to be
a scheduler.

## Decision 6 — health and readiness are not the same signal

PostgreSQL health is `pg_isready`; Ollama health is a successful local model
listing. Those signals only sequence startup. The runtime readiness job then
proves all of the following before declaring the deployment ready:

- PostgreSQL major 18 and pgvector exactly 0.8.6;
- both immutable B1/B6 migrations are recorded;
- Ollama exactly 0.32.5;
- `qwen3:4b` has the expected full digest and loads at 8,192 context within a
  finite ten-minute cold-load deadline;
- the attachment volume supports a create/fsync/delete canary;
- the event-spool key is exactly 256 bits and the authenticated spool opens.

The emitted report is metadata-only. Failed checks exit non-zero.

## Decision 7 — upgrade and rollback ownership

The operator sequence is: create and copy a verified backup; stage pinned
images/model artifacts; build or load the new application images; run forward
migrations once; start dependencies; run readiness; then attach/restart the
Phase C server when it exists. Application images may be rolled back only when
their schema compatibility is explicit. Database rollback is isolated restore
plus reconciliation and forward repair, not `dbmate down` on production.
PostgreSQL major upgrades require their own restore rehearsal, as B0 already
decided.

## On-premises versus private cloud

The trust contract is identical: the client owns the host, volumes, keys,
backup destination, firewall, and administrative identities. On-premises is
preferred for physical/data-boundary requirements or disconnected operation.
Private cloud is preferred when the client accepts that provider's control
plane and needs mature snapshot, monitoring, and hardware replacement. A
managed database, object store, or inference API changes the inventory and is
not a drop-in substitution under this ADR.

## Acceptance

- `npm run verify:deployment` renders every Compose profile and applies a
  fail-closed topology policy.
- Negative controls prove host ports, egress attachment, mutable database
  images, and secret-like environment variables are rejected.
- Typecheck, deterministic tests, and `git diff --check` remain release gates.
- Live build/start/migrate/model/readiness/backup evidence must be reported
  separately from the deterministic manifest result.
